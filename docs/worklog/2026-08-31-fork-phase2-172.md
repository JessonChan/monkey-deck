# 2026-08-31 fork Phase2 消费端(#172 / task #28908)

## 起因

#172 Phase1 探针(0cf4df6)实测完协议事实后,本卡做消费端:`session/fork`(UNSTABLE)全栈接入 —— runner 层 Fork RPC + forked_from 落库 + ChatService binding + ChatView/Sidebar 两个入口 + i18n + 双端测试。基于 main 最新 3431e13。

**三铁律(硬性,探针 0cf4df6 结论)**:
1. 门控以 `Fork.Declared` 声明位为准 —— 未声明**不渲染入口**(隐藏非禁用);错误响应仅作诊断,不假设 -32601(jcode 实测回过 -32603)。
2. 同 cwd fork —— 恒传源 session 的 worktree 路径,不新建 worktree、不改 baseRef。
3. forked session 串行使用 —— 源 prompting/executing 中后端拒绝 fork(忙错误);**fork 后源与 fork 的并发 prompt 不做运行时互斥**。已知风险:探针⑧ omp 在 fork 后并发双 prompt 下两轮均进程死亡(见 Phase1 报告),本期不做防护、不在 UI 层互斥,靠后端「源忙拒绝」+ 用户自觉;若后续实证并发崩溃成为常态,再评估 per-worktree 串行锁(记 OPEN)。

协议事实:fork 点恒为当前对话末尾(`session/fork` 无位置参数)——UI 文案按此收敛(「从当前对话末尾分叉」),不承诺历史位置。

## 改法

### 后端

**`internal/acp/runner.go`**
- `ChatSession` 增 `canFork bool`(Initialize 响应 `sessionCapabilities.fork != nil`,与 `CanListSessions` 同源同刻赋值)+ `mcpCaps acp.McpCapabilities`(fork 重建 MCP 注入列表用);`NewChatSession`/`ResumeChatSession` 两处都填 —— **resume 后的 session 同样可 fork**(声明位每次 spawn 现取)。
- `CanFork() bool` 方法(chatConn 接口面)+ `ErrForkNotDeclared` typed error(文案钉死 `harness does not advertise sessionCapabilities.fork`):未声明**不发 RPC** 直接拒绝 —— 错误响应码不可假设,声明位是唯一门控(铁律①)。
- `Fork(ctx, mcps []store.McpServer) (ForkResult, error)`:cwd 恒传 `cs.WorkDir`(源 worktree,铁律②);mcpServers 沿源(调用方传源落库的 MCP 选择,按 Initialize 协商能力过滤,与 New/Resume 同一 `mcp.ToAcpServers` 转换,不支持传输丢弃并告警)。
- `ForkResult{NewSessionID, ConfigOptions []ConfigOption}`:**configOptions 用内部已拍平的 `[]acp.ConfigOption`**,UNSTABLE→稳定归一(`unstableConfigOptions`)+ 既有 `FlattenConfigOptions` 全部收敛在 acp 层内 —— 业务包零 SDK 类型依赖(§2.1),消费与 NewSession/LoadSession 同一管线。响应的 `Modes` 无既有消费者(与 `ResumeSessionResponse.Modes` 同样被忽略),不透出。
- `toUnstableMcpServers`:稳定 McpServer → fork 要求的 UNSTABLE 线格式(stdio 同型直搬;http/sse name/url/headers 同型;acp 变体 id 类型转换),纯机械搬运,过滤已由 ToAcpServers 完成。

**`internal/store`(migration 0023)**
- `0023_session_forked_from.sql`:`sessions` 增 `forked_from TEXT NOT NULL DEFAULT ''`(与 base_ref/tags 同款 NOT NULL DEFAULT,免 NULL 扫描分支)。
- `Session.ForkedFrom`(json `forkedFrom`)入 struct + `sessionColumns` + `scanSession`(27 列,`TestSessionColumnsCount` 守卫同步 26→27)+ `SetSessionForkedFrom` setter(lineage 是元数据非内容活动,**不动 updated_at**,与 pinned/custom_title/tags 同理)。

**`internal/chat/chat.go`**
- `chatConn` 接口增 `CanFork() bool` + `Fork(ctx, mcps) (acp.ForkResult, error)`;`fakeChat`/`mockChatConn` 两个测试 mock 同步实现(fakeChat 的 canFork/forkResult/forkErr 可注入)。
- `ForkSession(sourceSessionID) (*store.Session, error)` 流:源存在校验 → **源忙拒绝**(`isBusy`,铁律③前半)→ `ensureLive`(未活跃则懒 spawn/Resume —— fork 需要持有源 ACP session 的活 harness,顺带取权威声明位)→ `CanFork` 门控(未声明 typed error)→ 取源 MCP 选择 → `ls.chat.Fork` → 新行落库:
  - project/model/harness 同源;worktree **沿源**(同 cwd,铁律②;worktreeKind 自然落 guest 角色,不碰 baseRef);
  - `forked_from` = 源 db id;title = 源显示标题(CustomTitle || Title)+ `" (fork)"`;
  - **立即 `UpdateSessionACP` 钉 fork 响应的新 ACP session id** —— fork 的上下文在 harness 侧(我们的 DB 不复制消息),下次 open 必须 Resume 进 forked session,绝不能当新 session 再 NewSession 丢上下文;
  - configOptions 以 **fork 响应自身**为准落 `config_options_cache`(探针⑤:回显一致但消费以响应为准,不假设);
  - 新行 status=idle 语义 = 无本地消息 + 懒 spawn,打开走既有 `session/load` 回放管线零特殊处理(探针④ load/resume 可用;本地无历史故 UI 显示空白属本期预期,forked_from 仅落库不做 UI 标识)。
