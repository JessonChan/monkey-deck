# 2026-08-31 fork 探针 Phase1(#172 / task #28905)

## 起因

#172 要给 monkey-deck 加「session fork」能力(acp-go-sdk v0.13.5 的 `session/fork`,UNSTABLE,types_gen.go:7702-7757)。Phase 1 不写产品代码,先把**事实**探清:哪些 harness **声明**了 fork 能力、未声明的强发 fork 会回什么 JSON-RPC 错误、已声明的 fork 往返在各家真实行为如何。产出是纯探针卡:`ConformanceReport` 增加 fork 段,报告四段组织(声明矩阵/错误码锚定/六问逐项/结论),供回贴 GitHub #172。

## 改法

### probe.go

- `ConformanceReport` 增 `Fork ForkReport`(Tier2,永不阻断 `CanAdd()`);`Summary()` 增 `[fork]` 行,N/A 项显式渲染 `n/a` 不与 `✗` 混淆。
- **P1 声明矩阵行**:`Fork.Declared = initResp.AgentCapabilities.SessionCapabilities.Fork != nil`(与 capability.go `matrixFromInit` 的 `SessionFork` 判据同源,但探针自持字段,不给 capability.go 引入消费者)。
- **P2 undeclared 强 fork**:构造最小 `UnstableForkSessionRequest{SessionId: 探针会话, Cwd: 探针 cwd}` 强发,锚定 `forced-fork: <code> <message>` 入报告;`ForceClass` 五分类:`method-not-found`(-32601)/ `invalid-params`(-32602)/ `other` / `no-answer`(超时断连,无 JSON-RPC 错误响应)/ `unexpected-success`(未声明却成功——声明与实现不一致,本身是发现)。undeclared 一律跳过 P3 往返,八项逐项落 `N/A: fork 未声明` 。
- **P3 declared 最小往返**:①新 id≠源 ②源仍可 prompt(提示词取最小 `hi`,防配额浪费)③`session/list` 含新 id(list 未声明→N/A)④新 id 可 `session/load`(未声明则 `session/resume`,都未声明→N/A)⑤fork 响应 configOptions 逐条 id/currentValue + modes 存在性/currentModeId 与源 NewSession 响应一致 ⑥cwd 语义:①即同 cwd fork,再以新 tmp cwd fork 一次记录行为差异(干净协议错误也算确定性观察判 pass;超时/断连判 fail)⑦fork 链(对 fork 结果再 fork)⑧源/fork 并发各一发 `hi` 观察互扰。
- **UNSTABLE 容错红线**:整个 fork 段包 `recover()`(panic → `Fork.Error`),每 RPC 硬超时 `probeForkTimeout = 20s`(prompt 走既有 90s turn 超时),任何单步失败只落 failed/N-A 行+原因,探针必收敛出报告。
- 前置失败(fork① 报错)时:NewID 保留 fork 错误原因,其余七项 N/A「前置 fork 失败」——绝不静默省略。

补充观察:
- **omp 的 fork 往返 ①-⑤⑦ 基本健康**,但⑧并发双 prompt 稳定杀死进程(两轮均复现;第 1 轮死在 fork 后首个 prompt,第 2 轮死在⑧并发段)——fork 后的 omp 进程对并发/后续负载脆弱,Phase 2 若消费 fork,**单线程串行使用 forked session,勿并发 prompt**。
- **junie**:声明 fork 且 Tier1 全过,但两轮均在 fork RPC 前进程退出(探针日志 `harness exited unexpectedly (crash)`),fork 往返未取得有效数据——疑似 junie 空闲自杀类稳定性问题,建议单独复测。
- **opencode / kimi**:本轮主 prompt 零流式产出(stream/turn ✗),进程在 fork 前死亡,fork 声明位有效但往返未取得数据——环境性失败(模型/认证),非 fork 语义结论,待环境恢复复测。
- 框架允许所有八项(无 N/A-by-design 项);undeclared harness 的八项按 P1 标注全部 N/A,未静默省略。

## 【结论】

1. **协议事实**:`session/fork` 是 UNSTABLE 扩展,声明位 4/8;未声明侧 -32601 是主流锚但非全部(jcode 回过 -32603);声明侧真正端到端可用的只有 omp,且其 forked session 在并发 prompt 下崩进程。
2. **Phase 2 设计输入**:
   - 门控以 `Fork.Declared` 声明位为准,错误响应仅作诊断(不假设 -32601);
   - fork 响应的 configOptions/modes 回显可按源会话一致预期(omp/fakeagent 均一致),但 Phase 2 的 model-select 等消费仍应以 fork 响应自身为准;
   - 换 cwd fork 在 omp 是确定性错误("fork was cancelled"),Phase 2 的 worktree 模型(§1.4,`md/<session-id>` 新目录作 fork cwd)**在 omp 上不可用,需以同 cwd fork + 不可换 cwd 为默认语义设计**,或仅对支持换 cwd 的 harness 开放;
   - forked session 必须串行使用(omp ⑧ 实证);
   - fork 链可用(omp ✓),但 UI 树需要防环(Phase 2 范围,此处只记录事实)。
3. **红线验证**:探针全程无 panic/挂起;undeclared 强 fork、peer 死亡、fork 被取消等异常均收敛为报告行+原因;每 RPC 硬超时。
4. Phase 2(消费者/UI/binding/forked_from/worktree 关系)不在本卡,未做任何实现。
