# #191 busy fork 放宽:卡内探针门(双阶段卡 #28965,阶段 A)

日期:2026-09-03
关联:#191(busy fork 放宽)、#172(fork 探针与三铁律)、#189/#190(水位 / custom_title,本次零波及)

## 起因

#191 想放开「源 session 正在对话中不能 fork」的限制(busy fork)。本卡是双阶段:**阶段 A 探针门(硬前置)**——turn 进行中 fork 的行为实测,fakeagent + 真实 omp 各跑四项;**阶段 B 实现**(仅 A 全过):删 `errForkSourceBusy`、fork 前强制 flush 拉齐水位、ChatView 按钮 busy 禁用态移除、探针场景沉淀。

判定规则(卡内拍板):四项全过 → 进阶段 B;**任一失败 → 停在探针**,worklog 记录四项实测 + 失败分析,不写任何实现代码,不删 `errForkSourceBusy`。

四项定义:

1. 源 turn 进行中发 fork RPC 是否成功;
2. fork 出的会话上下文是否包含进行中的部分回复(快照点到哪:含流式中内容 / 只到上一条完整消息 / 其他,如实记录);
3. 源 turn 是否被 fork 干扰(存活 / 中断 / 输出异常);
4. fork 后立刻串行 prompt fork 行为是否正常(fork 行可用)。

## 改法(探针代码,阶段 A 产物)

### `internal/acp/probe.go`

- `ForkReport` 增 busy-fork 四行:`BusyFork`(①)/`BusySnap`(②)/`BusySrcOK`(③)/`BusyForkUse`(④),Tier2 永不阻断 `CanAdd()`;undeclared 全落 `N/A: fork 未声明`(铁律①声明位门控)。
- `Summary()` 的 `[fork]` declared 行追加 `busy 中fork=✓/✗ 快照=… 源无扰=… fork可用=…`。
- 新增 `evCapture`(并发安全的 chunk 事件取证 + 「等待下一个 chunk」就绪信号):fork 触发时机锚定**真实流式开始**,不靠固定延时;`chunkTail` 取按 session(+可选 messageId)过滤的最长累积全文,供 Note 人话预览。
- 新增 `runBusyForkProbe`:发起长 prompt("Count from 1 to 40…")→ 第一个 chunk 到达即发 fork(①)→ load/resume fork 观察回放快照点(②)→ 等源 prompt 收敛判源是否被扰(③)→ 串行 prompt fork(④)。④ 有意排在源 turn 结束之后:铁律③「forked session 串行使用」,④ 测 fork 行本身可用,不与 P3 ⑧ 并发互扰混淆。
- 执行顺序:busy 段(3.w)**先于** P3 往返(3.x)——P3 ⑧ 并发双 prompt 在 omp 上有杀进程前科(#172 实测),前置 busy 段避免 ⑧ 崩溃污染 busy 四项归因。
- ② 的观察面:load/resume fork 的回放内容 = harness 侧复刻给 fork 的上下文。同 messageId 过滤(busyMsgID 取自本轮首个 chunk,§5.4 #10 主键归并)= 回放保留原 id 的 harness(omp/fakeagent)的精确观察;过滤空但全量有回放时如实标注(回放换发新 messageId 的形态)。

## 判定:探针未过,停在探针

**omp ① 失败(两轮确定性复现)→ 探针门未过,阶段 B 不执行。**

失败分析:

1. **omp 在协议层显式拒绝 busy fork**。错误是确定性状态守卫("fork is unavailable while a prompt is in progress"),不是竞态、不是崩溃、不是配额/网络问题——两轮不同 session id、同一拒绝语。
2. **放宽对 omp 无效**:monkey-deck 即使删掉自身 `errForkSourceBusy` 前置拒绝,`session/fork` RPC 到了 omp 也必然收到 `-32603`。产品效果只会把「可预期的本地提示(源会话忙)」换成「harness 错误 toast」,体验更差。
3. **#191 的前提在当前唯一端到端可用的 harness 上不成立**(#172 实测声明侧真正跑通 fork 往返的只有 omp)。②③④ 因此在 omp 上不可观测(fork 没发生,没有快照点可言)。
4. 水位语义未动:阶段 B 取消,fork_base_seq 仍恒为「源空闲时的最大 seq」(#172 Phase 3 / #189 不变量),不存在「含进行中落库部分」的新语义。

按卡内红线:不写任何实现代码,`errForkSourceBusy` 未删,`internal/chat`、前端、AGENTS.md §5.4 #14 零改动。
